### Interpretation and caveats
- The original engine-only cycles:u profile had 75 samples, zero reported
  lost samples, and approximately 56 minutes between first/last samples.
  Insufficient for reliable hotspot rankings; some frames were unresolved
  or suspicious. Do not optimize from its percentages alone.
- Real-time replay lasts about 61 minutes. Sparse events yield little
  active engine CPU time. Check sample adequacy in a short pilot before
  asking the operator to repeat a long profile.
- Wait/spin/probe affect both engine and network policies. Results do not
  isolate engine waiting alone.
- Different streams can produce different combined ingress orders.
  Probe also advances eviction using synthetic feed time.
  Different execution totals do not prove a bug in probe.
- Earlier source review found different TCP/gRPC TTO start boundaries:
  TCP before application decoding; gRPC after delivery/conversion.
  Recheck current code before claiming equivalent transport measurements.
- RTT plots use latency_ns and include all recorded statuses.
  Check response semantics, trade IDs and statuses before causal comparisons.
- Profiling-session latency is not the final unprofiled benchmark.
- Repeating a transport/mode overwrites its outputs in the build directory.
  UDP multicast uses TCP OE filenames and can overwrite TCP/mode results.

### Follow-up priorities
Review current source before changes: the archive reviewed in chat predates
the execution-mode implementation.

1. Investigate TCP recvMarketEvent allocating a new vector per receive.
   Reuse reserved storage or a bounded buffer; preserve decoder semantics.
2. Check SendAll retrying indefinitely on EAGAIN: a slow reader could
   monopolize the network thread. Preserve offsets and return to the loop.
3. Check receive-drain fairness under sustained ingress and bursts.
4. Add optional per-stage latency timestamps and deterministic ingress replay
   to separate computation, queue delay, wake-ups and decision differences.
5. Verify whether HALT only sends a status message or actually gates decisions.
6. Validate denser profiling workloads without silently changing event-time
   semantics; preserve sparse replay as a separate benchmark.

Do not change machine power policy, kernel settings or CPU isolation without
the owner's authorization. Never assume native Linux must outperform Docker
without matching workload, hardware and measurement boundaries.
